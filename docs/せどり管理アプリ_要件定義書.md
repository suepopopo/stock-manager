# せどり管理アプリケーション 要件定義書

- 作成日：2026年7月22日
- バージョン：1.0（第一フェーズ）

---

## 1. 目的・概要

現行はCSV/Excelでの手動管理を行っているが、入力の手間と時間がかかるため、Webアプリ化により業務を効率化する。あわせて、蓄積した仕入・売上データをもとに確定申告の作業負担を軽減し、正確な在庫・損益管理を実現することを目指す。

第一フェーズでは「マスタ管理」「取引（購入商品）登録」「利益の見える化（月次収益確認）」までを実現し、業務の可視化と記帳の効率化を図る。複数ユーザーでの同時ログイン・権限分離は現時点では不要（単一/少数の固定アカウント運用でよい）。一方でPCだけでなくスマートフォンからも確認できるようにしたいため、レスポンシブ対応は必須とする。
第二フェーズ以降で、外部データ取得（買取相場）や確定申告支援機能へと拡張する。

### 開発フェーズ概要

| フェーズ | 内容 |
|---|---|
| 第一フェーズ（本書対象） | マスタ管理・購入商品登録・利益計算・月次収益確認 |
| 第二フェーズ | 買取相場スクレイピング・グラフ表示・過去データ参照 |
| 第三フェーズ | 確定申告支援（支出/イレギュラー収入記帳、販路別・仕入れ先別集計） |

---

## 2. 前提・非機能要件

| 項目 | 内容 |
|---|---|
| 実行環境 | さくらのVPS（1GBプラン）で常時稼働。Node.jsアプリ・PostgreSQLともにDockerを使わずVPS上に直接インストールし、systemdでプロセス管理する（メモリ消費を抑えるため）。個人利用（基本的に自分のみ）を想定 |
| 認証方式 | Basic認証（ID・パスワードによる簡易アクセス制御） |
| データベース | PostgreSQL（VPSに直接インストール、systemd管理） |
| 対応デバイス | PC・スマートフォン両対応（レスポンシブ対応必須） |
| バックアップ | DBファイルの定期的な手動/自動バックアップを推奨（詳細は設計時検討） |

### 2.1 テーブル共通カラム方針

全テーブルに以下を共通で持たせる。

| カラム | 内容 |
|---|---|
| id | 主キー（serial/auto increment） |
| delete_flag | 論理削除フラグ（物理削除は行わない） |
| created_at | 作成日時 |
| updated_at | 更新日時 |

作成者／更新者カラム（created_by/updated_by）は、利用者が少数の固定アカウントであることを踏まえ、第一フェーズでは持たせない。

## 3. 機能要件（第一フェーズ）

### 3.1 認証機能

- Basic認証によりアプリ全体へのアクセスを制御する。
- ユーザー管理は簡易的（単一または少数の固定アカウント）でよい。

### 3.2 商品登録機能（商品マスタ）

商品そのものの情報を管理するマスタ。

| 項目名 | 説明 | 必須 |
|---|---|---|
| 正式商品名 | 商品の正式名称 | ○ |
| 省略表示名 | 一覧などで使う短縮名 | - |
| JANコード | 商品識別用のJANコード（ギフトカード等JANが無い商品もあるため任意項目。ただしユニーク制約あり） | - |
| 商品カテゴリ | 商品カテゴリ | - |

**備考**
- JANコードが入力された場合は重複チェックを行い、同一JANの商品は既存扱いとして紐付ける。

### 3.3 支払い方法登録機能（支払い方法マスタ）

支払い手段の種類のみを管理するシンプルなマスタ。

| 支払い方法名 |
|---|
| クレジットカード |
| ギフトカード |
| 現金 |
| 振込 |
| ポイント |

**備考**
- 「複数払い」という区分は廃止。1回の仕入れで複数の支払い方法を組み合わせた場合は、3.3.2「支払い内訳」側で複数行に分けて記録する。

#### 3.3.1 クレジットカードマスタ

| 項目名 | 説明 |
|---|---|
| アカウント | カードの持ち主（本垢／嫁垢等）。account_idと同じ設定ファイル方式（例: `config/accounts.ts`）で管理し、DB外部キーではなくアプリ側で解決する |
| ブランド | Visa／Amex／JCB 等（項目数が少ないため設定ファイルで管理する想定。他の設定ファイル方式のマスタ（アカウント等）と統一） |
| カード名 | 楽天ゴールドカード、ヒルトンカード等の正式名称 |
| カード番号 | 下4桁のみ保持（セキュリティ上、完全な番号は保持しない） |
| 表示名 | 一覧表示用の短縮名（例：楽天ゴールド(h)、JCB白(h)） |
| 名義 | カード名義人 |
| ステータス | 契約中／解約済 |
| 入会日 | カード入会日 |
| 解約日 | 解約した場合の日付（未解約の場合は空欄） |
| 年会費有無 | 年会費の有無 |
| 年会費金額 | 年会費有無が「有」の場合の金額 |
| 年会費支払日 | 年会費の引き落とし日 |
| 備考 | 自由記述 |

#### 3.3.2 支払い内訳（購入商品登録に対して1対多）

1回の仕入れに対し、「支払い方法×金額」の組み合わせを複数行で記録できるようにする（point_detailsと同様の考え方を支払い全般に拡張）。

| カラム | 内容 |
|---|---|
| 支払い方法 | 支払い方法マスタ参照 |
| 金額 | この支払い方法で払った金額 |
| クレジットカード | 支払い方法が「クレジットカード」の場合のみ、クレジットカードマスタ（3.3.1）を参照 |
| ポイント種別 | 支払い方法が「ポイント」の場合のみ、ポイント種別マスタ（3.6）を参照。何のポイントで支払ったか後から追えるようにするための項目 |
| メモ | 自由記述（任意） |

例：ギフトカード10万円＋PayPayポイント5万円で仕入れた場合 → 内訳2行（①ギフトカード／10万円、②ポイント／PayPayポイント／5万円）。

#### 3.3.3 クレジットカード支払い管理

購入商品登録からの自動集計ではなく、カード明細を見ながら手動で請求額を入力・確認するための台帳ページ。現行Excelの「クレジットカード×請求月」のマトリクス管理（カードをアカウント単位でグルーピングし、月ごとの請求額を入力）を踏襲する。

| 項目名 | 説明 |
|---|---|
| クレジットカード | クレジットカードマスタ（3.3.1）参照。アカウント・支払日はマスタから引き継いで表示・グルーピングに利用する |
| 対象年月 | 請求対象の年月 |
| 請求予定額 | 明細を見て手動入力する請求額 |

- 画面はカード×年月のマトリクス形式（アカウントごとにグルーピング、アカウント単位の月次小計を表示）。
- 支払済みフラグは持たない。

### 3.4 販売先登録機能（販売先マスタ）

| 項目名 | 説明 | 必須 |
|---|---|---|
| 法人番号 | 販売先の法人番号（確定申告での利用を想定）。取得できない販売先もあるため任意項目 | - |
| 会社名 | 正式企業名 | ○ |
| 店名 | 店舗/ショップの表示名（モール出店名、Yフリマ等） | ○ |

**備考**
- 1レコード＝1店舗（販売先）とする。同一法人が複数店舗を持つ場合、法人番号・会社名は行ごとに重複して持たせる（法人と店舗を別マスタに分けるほどの規模ではないため）。

### 3.5 仕入れ先登録機能（仕入れ先マスタ）

仕入れ先は階層構造で管理する。仕入れ区分・モール/カテゴリは項目数が少なく将来も増えない想定のため設定ファイルで管理し、②仕入れ先名のみDBマスタとする。

**構造イメージ**

```
仕入れ区分（EC or 店舗）※設定ファイル管理
├─ ECの場合
│   └─ ①モール/カテゴリ選択（ヤフーショッピング／楽天市場／Amazon／各種公式オンラインショップ）※設定ファイル管理
│       └─ ②具体的な仕入れ先（ヤマダデンキ、エディオン、カメラのキタムラ 等）※DBマスタ
└─ 店舗の場合
    └─ ②と同じ「具体的な仕入れ先」を直接選択
```

| 項目名 | 説明 | 管理方式 |
|---|---|---|
| 仕入れ区分 | EC／店舗 | 設定ファイル |
| ①モール/カテゴリ | ECの場合のみ選択（ヤフショ／楽天市場／Amazon／公式オンラインショップ 等） | 設定ファイル |
| ②仕入れ先名 | 具体的な仕入れ先名（予測変換入力＋新規追加ボタン） | DBマスタ |

**入力UI要件**
- ②の仕入れ先名は予測変換（オートコンプリート）形式の入力とし、候補にない場合は横の「新規追加」ボタンから即時マスタ登録できるようにする。
- 店舗仕入れの場合はモール/カテゴリ選択をスキップし、直接②の仕入れ先名選択に進む。

### 3.6 ポイント種別登録機能（ポイント種別マスタ）

| 項目名 | 説明 |
|---|---|
| ポイント種別名 | PayPay／楽天ポイント／WAON 等 |

**入力UI要件**
- 仕入れ先マスタと同様、予測変換入力＋新規追加ボタンによる登録方式とする。

### 3.7 購入商品登録機能

上記マスタ（商品／支払い方法／販売先／仕入れ先／ポイント種別）を利用して、実際の仕入れ〜販売の1取引を登録する。現行CSVの列を踏襲しつつ、可変件数の内訳（支払い・ポイント）はマスタ側の1対多構造に寄せる。

| 項目名 | 説明 | 参照/管理方式 |
|---|---|---|
| 商品 | 対象商品（商品名・JANは商品マスタから参照） | 商品マスタ |
| グループID | 複数商品をまとめて1回で売却した場合に同じIDを振る（同一グループIDの行が複数存在してよい）。単独売却の場合は不要 | - |
| アカウント | 仕入れに使った自分たちの口座 | 設定ファイル（`config/accounts.ts`） |
| 購入サイト | ①モール/カテゴリ（ECの場合のみ） | 設定ファイル |
| ショップ（仕入れ先） | ②具体的な仕入れ先店舗 | 仕入れ先マスタ |
| 仕入れ価格 | 仕入れ時の金額 | - |
| 仕入れ日（購入日） | 仕入れた日付 | - |
| 支払い内訳 | 支払い方法×金額の組み合わせ（複数行） | 支払い内訳（3.3.2） |
| ポイント内訳 | 仕入れ時に得たポイントの種別・金額（複数行、CSVでは3枠固定だったがDBでは件数無制限） | point_details |
| ポイント還元合計 | ポイント内訳の合計額 | 自動計算 |
| 実質価格 | 仕入れ価格 − ポイント還元合計 | 自動計算 |
| 販売先 | 販売した先 | 販売先マスタ |
| 売上価格 | 販売時の金額 | - |
| 販売日 | 販売した日付（未販売の場合は空欄可） | - |
| 到着済みチェック | 商品が到着したか（true/false） | - |
| 売却チェック | 売却済みか（true/false） | - |
| ステータス | 到着待ち／保有中／売却済み（下記ロジックで自動判定、手動選択はさせない） | 自動計算 |
| 利益 | 自動算出（3.8参照） | 自動計算 |
| 利益率 | 自動算出（3.8参照） | 自動計算 |
| 備考 | 自由記述 | - |

**ステータス自動判定ロジック**

| 条件 | ステータス |
|---|---|
| 到着済みチェック = false | 到着待ち |
| 到着済みチェック = true かつ 売却チェック = false | 保有中 |
| 売却チェック = true | 売却済み |

**備考**
- 手数料（販売手数料・送料等）は項目として持たない（現行CSVにも無いため）。

### 3.8 利益計算機能

- 購入商品登録の情報をもとに、1件ごとの利益・利益率を自動算出する。
- 算出ロジック：
  - `ポイント還元合計 = Σ ポイント内訳.金額`
  - `実質価格 = 仕入れ価格 − ポイント還元合計`
  - `利益 = 売上価格 − 実質価格`
  - `利益率 = 利益 ÷ 売上価格 × 100`

### 3.9 簡易的な月々の収益確認ページ

- 月単位での「仕入れ合計額」「売上合計額」「利益合計額」を一覧表示する。
  - 仕入れ合計額：その月の**仕入れ日**基準で集計
  - 売上合計額・利益合計額：その月の**販売日**基準で集計
  - （仕入れと売上は別基準で月を区切るため、同月内で仕入れたものが翌月以降に売れた場合、仕入れ合計は仕入れ月、売上・利益合計は販売月にそれぞれ計上される）
- 対象月の切り替え（前月／翌月ナビゲーション、または月選択）ができること。
- 第一フェーズではグラフ等の高度な可視化は不要、テーブル形式の簡易確認で良い（グラフ表示は第二フェーズ）。

## 6. 今後の検討事項（要確認）

- データのバックアップ／エクスポート機能の要否（CSV出力等）：第一フェーズではスコープ外とし、設計時以降に先送り

**決定済み（参考）**
- 商品マスタは1件、購入商品登録（stock_items）は複数件という設計で確定（同一商品を複数回仕入れても商品マスタは増えない）
- ポイント還元は「実質価格 = 仕入れ価格 − ポイント還元合計」として利益計算に算入（3.8）
- 複数払いの内訳は3.3.2「支払い内訳」として1対多で構造化済み
- 仕入れ先マスタの「EC/店舗」区分・①モール/カテゴリは設定ファイルで管理（3.5）
